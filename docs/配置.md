# 配置

## 一、NapCat 那边

插件连的是 NapCat 的 OneBot11 **WebSocket 服务端**，不是 HTTP。

1. 打开 NapCat 的 WebUI（默认 `http://localhost:6099`），进「网络配置」；
2. 新建一个 **WebSocket 服务器**：端口自定（本文用 `3001`），Token 自己设一串；
3. 保存后 NapCat 会重启那个连接；确认端口在听：`Test-NetConnection 127.0.0.1 -Port 3001`。

> WSL 里的 NapCat 要注意：**WSL 停了，端口就没了**。先 `wsl -l -v` 看是不是 `Running`。
> 启动脚本是幂等的：返回 `10` 表示「已经在跑」，这时它**不会重载配置**——改完配置要先把
> `qq` / `xvfb-run` / `screen` 全杀掉再启动。

## 二、插件配置项

放在 profile 的 `cordis.patch.yml`（或插件自己的 `cordis.patch.yml`），见 `examples/cordis.patch.yml`。

| 键 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `wsUrl` | string | `ws://127.0.0.1:3001` | NapCat 的 WS 地址 |
| `token` | string | `""` | 与 NapCat 里那串一致；空 = 不带 Authorization |
| `owners` | number[] | `[]` | **必填**。只接这些 QQ 号的私聊；空 = 全忽略 |
| `cwd` | string | `""` | AI 的工作目录；空则用 `DSH_WORKSPACE`，再空则 `process.cwd()` |
| `earScript` | string | `""` | 转写脚本路径；不配 = 语音只留占位 |
| `tmpDir` | string | `<系统临时目录>/dsh-qq` | 收到的图片/语音落这里 |
| `stateDir` | string | `""` | 空则用 `<DSH_HOME>/qq` |
| `maxChars` | number | `1800` | 一条消息最多多少字，超了切段 |
| `provider` | string | `""` | 建议显式写，例如 `deepseek-account` |
| `model` | string | `""` | 建议显式写，例如 `deepseek-flash` |
| `sessionId` | string | `""` | 填了就把 QQ 接进这间；空 = 第一次消息时自建 |
| `groupMessages` | boolean | `false` | 群消息是否也当输入（默认只记日志） |

### 为什么要显式写 provider / model

DSH 的 `agent-default-model` 可能指向本地服务（例如 llama.cpp 的 `127.0.0.1:9931`）。
本地服务没起时，QQ 会话一发消息就是 `503 acp-proxy failure: connect-refused`。
QQ 这条链路要的是「随时能回」，所以建议固定走云端。

## 三、语音转写（可选）

`earScript` 指向任意可执行脚本，约定：

```
node <earScript> <音频文件路径>
```

stdout 里出两样，插件按前缀取：

```
这行是转写文本
[语气] 时长 2.78s · 语速 7.19/s · 停顿 2 处 · 句尾上扬 · 唤醒度 偏高
```

- 只有 `[语气]` 开头的行会被当成语气；其它行拼起来当转写。
- 两样都没有 = 这条语音记成「转写失败」。
- 微信的语音是 SILK，QQ 的是 AMR，都要先解成 wav 再喂给 ASR；插件只负责把音频文件路径给你。

参考实现（作者的用法）：`ffmpeg` 解 → `faster-whisper` 转写 → `dsh-ears-prosody` 出声学层。
